# preparatory-refactoring クイックガイド: 機能を足す前に「整理するか」を決める

「この機能を足したいが、先にコードを整理したほうがいいのか」「整理するならどこまでか」。この迷いに、手順と実測で答えを出すのが preparatory-refactoring スキルです。このガイドを読むと、スキルを入れて 4 つのモードを使い分け、出てきた計画の読みどころが分かります。

対象読者: Claude Code などのコーディングエージェントで既存コードを変更していて、リファクタリングを「やりすぎる / やらなすぎる」の両方に困っている開発者。

## 前提: 整理は目的ではない

このスキルは「コードをきれいにする」ためのものではありません。**特定の振る舞い変更（機能追加・不具合修正）を安く安全に入れるために、必要な分だけ構造を整える**ためのものです。「構造改善なし」も正当な結論として扱います。

区別は 1 つだけです。

- 構造改善: 戻り値、副作用、例外、出力、公開 API を変えない変更
- 振る舞い変更: それらのどれかを変える変更

両者は別コミット・原則として別 PR にします。

## 1. インストール

Node.js 22.20 以降と、同梱スクリプト用の [uv](https://docs.astral.sh/uv/) が必要です。

```bash
# Claude Code 向けに、全プロジェクトで使えるように入れる
npx skills add 53able/preparatory-refactoring -g -a claude-code
```

このリポジトリを clone した場合は、同梱スクリプトの自己テストで動作を確認できます。

```bash
cd skills/preparatory-refactoring/scripts && uv run python -m unittest test_change_coupling
# Ran 33 tests ... OK
```

## 2. 4 つのモードを依頼文で使い分ける

モードは依頼文から選ばれます。コードを変更するのは実行モードだけです。

| やりたいこと | 依頼の例 | モード | コード変更 |
|---|---|---|---|
| 整理すべきかを判断したい | 「X を追加したい。先に整理すべき？計画を書いて」 | 計画 | しない |
| 判断から実装まで任せたい | 「X を実装して。必要なら整理も」 | 実行 | する |
| 混ざった PR を分けたい | 「この PR、refactor と feature が混ざっているので分け方を提案して」 | レビュー | しない |
| 負債の返済順を決めたい | 「技術的負債をどこから返すべき？」 | バックログ | しない |

最初は**計画モード**で試すのが安全です。コードに触れずに、判断の根拠と計画だけが出てきます。

## 3. 計画で何が起きるか

計画・実行モードでは、次の順に進みます。

1. **変更を一文にする**: 「<誰 / 何> が <条件> のとき <新しい振る舞い> になる」。一文にできなければエージェントが確認してきます。
2. **事実を確かめる**: 「存在しない」「呼ばれている」といった主張は、検索コマンドか `file:line` 付きで事実確認表に載ります。確認できなかったものは「未確認」と書かれます。
3. **git 履歴で実測する**: 同梱の `change_coupling.py` で、よく変わるファイル（ホットスポット）と、一緒に変わるファイルの組（change coupling）を集計します。
4. **原因を診断し、タイミングを決める**: 改善候補ごとに「前に行う / 直後に行う / 後回し / 行わない」を選びます。
5. **順序つきの計画にする**: 各項目に `[テスト]` `[構造]` `[振る舞い]` のラベルが付きます。

### 履歴の実測で何が分かるか

スキルに同梱の評価用リポジトリ（請求処理、7 コミット）で実行した結果の抜粋です。

```bash
uv run "$SKILL_DIR/scripts/change_coupling.py" --repo . --partner api/schema.py --top 5
```

```text
WARNING: 分析対象コミットが 7 件しかない（目安 30 件以上）。...

## partner: api/schema.py (変更 3 回)
  together   ratio  path
         3    100%  report/monthly.py
         2     67%  billing/invoice.py
         2     67%  billing/money.py
```

`api/schema.py` と `report/monthly.py` は 3 回とも一緒に変わっています。しかし両者に import の関係はありません。中を見ると、どちらも通貨の一覧 `"USD", "EUR"` を別々に持っていました。import をたどるだけでは見えない**暗黙の依存**で、「通貨を追加するなら両方を変える」ことが履歴から分かります。

コミットが少ないと警告が出ます。その場合、割合は傾向の参考に留めます。

### 「整理しない」で終わらせないための判定（D1〜D3）

エージェントは「今回は整理不要」と結論しがちです。そこで、次の条件のどれかに当てはまれば構造改善を「前」か「直後」に必ず入れます。

- **D1**: 本番コードの 2 か所以上から使われている判定・計算の、既存の条件や式を書き換える
- **D2**: 引数を足すと、lint / 型検査の閾値（例: pylint `max-args` = 5）を超える
- **D3**: 5 行以上の重複したブロックの、3 つ目のコピーを作る

例外を認める理由は型が決まっています。たとえば「既存の式は変えず、分岐を足すだけ」なら D1 は打ち消されます。「呼び出し元が少ない」「変更頻度が低い」は打ち消しになりません。

## 4. 出てきた計画の読みどころ

計画のうち、次の 3 か所を確認すれば判断の妥当性を検証できます。

1. **結論の `なし判定:` 欄**: D1〜D3 それぞれが「非発火」「発火→打ち消し（事実 #n）」「発火→構造改善あり」のどれになったか。
2. **事実確認表の「判定」列**: 結論が「未確認」の事実に依存していないか。
3. **`[構造]` 項目の 3 欄**: 「楽になる部分」「変わりうる振る舞い」「固定する方法」が具体的か。楽になる部分を一文で書けない改善は、計画から外れて後回しリストに行きます。

## 5. 使わない場面

- 全面的な書き換え
- 性能チューニングだけの作業
- フォーマッタやリンタの設定だけの作業
- 要件定義

新しい抽象の導入やモジュール分割のような大きな変更は、このスキルの準備作業には含まれず、「範囲外の別計画」として分けて出力されます。

## 次の一歩

手元のリポジトリで、近く入れる予定の変更を一つ選び、計画モードで依頼してください。

```text
<機能> を追加したい。先に整理すべきか判断して計画を書いて。まだコードは変更しないで。
```

詳しい判断基準は `skills/preparatory-refactoring/SKILL.md` と `references/` にあります。
