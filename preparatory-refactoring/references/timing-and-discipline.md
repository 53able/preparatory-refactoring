# タイミングの判断と実行の規律

読む範囲の正本は SKILL.md の「モードと読む範囲」表。モード別に読む節:

- 計画モード: タイミング判断に迷ったときだけ、1〜2 節を読む。
- 実行モード: 3 節（実行の規律）が必読。4 節（停止条件）は SKILL.md の要約で足りる。
- 5 節（絡まったときの立て直し）: 構造改善と振る舞い変更が混ざったときに読む。
- レビューモード: 3 節の「見落としやすい振る舞い変更」を、紛れ込んだ振る舞い変更の照合に使う。

## 1. タイミングの 4 択

| 選択 | 選ぶ場面 |
|---|---|
| 前に行う | 改善すると目的の変更が明らかに安く・安全になる。改善の中身が分かっている。今のコードが理解できず、目的の変更を正しく書ける自信がない |
| 直後に行う | 目的の変更を入れた結果、同じ箇所への次の変更（予定がある、または履歴上よく変わる）を楽にする改善。目的の変更を入れて初めて正しい形が見えた場合や、急ぎの変更を先に届ける必要がある場合もここに入る |
| 後回しリストに記録 | 目的の変更で触っていない箇所の改善。次の変更を具体的に言えない改善。規模が大きい（範囲外の別計画）。今回の PR 系列の範囲を超える |
| 行わない | そのコードは今後ほぼ変わらない（履歴上の変更回数が少なく、予定もない）。近いうちに削除・置換される。改善の効果を説明できない |

ただし、SKILL.md 手順 4 の D1〜D3 が発火し有効な打ち消しがない場合、対応する構造改善は「後回し」「行わない」を選べない（「前」か「直後」のみ）。打ち消しが成立した Dn と、発火しなかった候補は、この表のとおり選べる。

「直後」と「後回し」の判別: 次の 3 つをすべて満たせば「直後」、1 つでも欠ければ「後回し」。

1. 対象が、目的の変更で触った箇所（同じ関数・同じファイル）である。
2. その箇所への次の変更を一文で言える（予定されている、またはホットスポット上位でよく変わる）。
3. 改善がその次の変更のどこを楽にするかを一文で書ける。

### 構造改善なしという結論

「構造改善なし」とは、目的の振る舞い変更の「前」または「直後」に予定した構造改善が 0 件の計画を指す（SKILL.md 手順 4 と同じ定義）。結論にする前に SKILL.md 手順 4「『構造改善なし』の反証（D1〜D3）」で発火条件を判定する。発火して有効な打ち消しのない Dn があれば、対応する構造改善を「前」か「直後」に入れ、「構造改善なし」は結論にしない。そうした Dn が無く、すべての候補が「後回し」か「行わない」になったときの「構造改善なし」は、手順の失敗ではなく正当な判断である。次のように書く。

- 計画の冒頭（結論）に「構造改善なし」と明示し、`なし判定:` 欄に D1〜D3 それぞれの判定（非発火 / 発火→打ち消し 事実 #n）を書く。`[構造]` 欄・停止条件・時間の上限には「該当なし（構造改善なし）」とそのまま書く（文言は固定。言い換えない）。
- 理由を書く: 比較の向き（例: 「改善 40 分 + 変更 10 分 > 改善なし 20 分」）、回収の見込み（例: 「このファイルは 12 か月で 2 回しか変わっていない」）、目的の変更が 1〜2 か所で素直に書けること、など。これらは「なし」の理由にはなるが、Dn の打ち消しにはならない（呼び出し元が少ない、変更頻度が低い、機能の中で一緒に変えれば足りる、は打ち消しではない）。
- 「振る舞い変更のコミット分割」行を必ず書き、振る舞い変更そのものの分け方を示す。例: (1) `test:` 既存の配送料を固定する特性テスト、(2) `feat:` 離島追加料金、(3) `chore:` 料金表の設定値追加。PR は 1 つでよいか、設定変更を別 PR にするか（反映の時期が違うなど）も書く。

## 2. 判断材料

精密な見積もりは不要。比較の向きが分かればよい。次の問いに順に答え、結論の根拠として計画に書く。

1. 費用の比較: 「改善の手間 + 改善後に目的の変更を入れる手間」は「改善なしで目的の変更を入れる手間」より小さいか。大小の向きだけ書く（例: 「改善 30 分 + 変更 30 分 < 改善なし 2 時間」）。
2. 後続での回収: 同じ場所を近いうちにまた変える予定・見込みがあるか。履歴のホットスポット上位なら、1 回では元が取れなくても数回で回収できる。
3. 理解への効果: 改善すること自体が、今のコードを理解する作業になっているか。読んでも分からないコードは、名前を直し入れ子を平らにしながら読むほうが早い。
4. 確信の有無: 何をどう直せばよいか分かっているか。分かっていないなら、改善より先に調査（読む、特性テストを書く）を行う。
5. 後回しの費用: 後でやると高くつくか。今は文脈が頭に入っているが、数週間後には忘れる。並行している他の変更と衝突しやすい場所か。
6. 今後の変更見込み: そのコードはこの先も変わるか。変わらないなら、どれほど読みにくくても改善の価値は低い。
7. 早く届けることとの釣り合い: 目的の変更を今日出す必要があるなら、改善は最小限（目的の変更が書ける程度）に留め、残りは直後か後回しへ。将来の変更が頻繁に予想されるなら、改善に時間を割く価値が上がる。
8. 結合を解く費用: 結合を減らす構造（変換層、対応表、引数での受け渡し、公開面の整理）にも費用がある。ある種類の変更に対する結合を減らすと、別の種類の変更に対する結合や、読むときにたどる間接が増えることがある。例: 料金計算を地域ごとの対応表に分けると地域の追加は 1 行で済むが、全地域に共通の計算式を変えるときは表のすべての行を確かめることになる。「結合したまま目的の変更を入れる費用」と「結合を解く費用 + 解いた後の変更費用」を比べ、前者が安ければ解かない。結合を限界まで減らそうとしない。
9. 広がる決定かどうか: 単体では簡単に戻せる決定でも、コード全体に広がると実質的に戻せなくなる。ID の型（整数か文字列か）、日時の表現（タイムゾーン付きか、エポック秒か）、共通ライブラリの選択、エラーの表し方（例外か戻り値か）などが典型。目的の変更がこうした決定を新しく持ち込む、または既存の決定をさらに広げるなら、広がる前に少し時間を取って考える。すでに広がった決定を戻すときは、一度に置き換えず、1 か所ずつ置き換える小さな改善を積み重ね、どこで止めても動く単位で進める（techniques.md の M17 と「範囲外の別計画」の段階を使う）。

### 比較が不利でも「前に行う」を選ぶとき

費用の比較で改善なしのほうが安くても、「前に行う」を選んでよい場合がある。ただし理由を明記する。例:

- 改善なしで書くと、同じ判定を 4 か所目にコピーすることになり、次回以降の変更で確実に漏れが出る。
- 今のコードでは目的の変更のテストが書けず、M15 で入力を引数にしないと正しさを確認できない。
- 来月に同じ箇所への機能追加が 2 件予定されている。

理由を書けない場合は「直後」か「後回し」を選ぶ。

## 3. 実行の規律

### 着手前

- 目的の変更で触る範囲に、振る舞いを固定するテストがあるか確認する。
- なければ特性テスト（現在の振る舞いをそのまま記録するテスト）を先に書く。期待値は仕様から考えずに、今のコードを実行して得た値を書く。明らかなバグに見えても、そのまま記録する（バグ修正は別の振る舞い変更として扱う）。
- 特性テストの追加も独立したコミットにする。
- 計画の各 `[構造]` 項目に書いた「変わりうる振る舞い」と「固定する方法」を見直し、固定する方法（テスト、手動確認の手順）をこの時点で用意する。

### 進め方

- 1 コミット 1 改善。コミットメッセージの先頭に種別を付けると、後でレビューと分割がしやすい（例: `refactor:` / `feat:` / `fix:` / `test:`）。
- 構造改善と振る舞い変更は別コミット。原則として別 PR にする。構造改善の PR を先に出し、振る舞い変更の PR をその上に積む。
- 各コミットの後にテストを通す。通らなければ、そのコミットを直すより取り消してやり直すほうが早いことが多い。
- PR は小さく保つ。目安はレビュアーが一度に読み切れる量（数百行以内）。
- 時間の上限: 「前に行う」構造改善は合計 1 時間程度を目安にする。超えたら手を止め、「目的の変更を簡単にする最小限の改善」に絞れているか見直す。絞れていなければ、残りを直後か後回しリストへ移す。それでも 1 時間を超える場合（例: 特性テストを書くための入力の差し替えに時間がかかる、目的の変更の前提として M17 の拡張段階が必要）は、理由を計画に書く。
- PR 説明には、構造改善によって次の変更が何か所・どの程度で済むようになるかを具体的に書く（例: 「地域判定が 3 ファイルに散っていたのを `isRemoteArea()` に集めた。離島料金の追加はこの関数と料金表の 2 か所で済む」）。構造の価値は機能と違って外から見えにくいので、書かないとレビュアーは費用だけを見ることになる。

### まとめる量

- 1 つの PR に入れる構造改善の数が増えるほど、次の問題が増える: 並行して進む他の作業との衝突、気づかないうちに混ざる振る舞いの変化、目的と関係のない改善。
- レビュー 1 回あたりの固定費（依頼、待ち時間、CI、承認手続き）が大きいと、まとめて出したくなり PR が大きくなる。大きな PR はレビューに時間がかかり、待ち時間がさらに延び、次の PR もまた大きくなる。
- 対策: 構造改善は小さな PR に分けて出す。チームの合意が得られるなら、構造改善だけの小さな PR は確認を軽くする運用（例: 承認者 1 名、変更が振る舞い不変であることの説明とテスト通過を条件に早めにマージ）を提案する。合意がない段階で、エージェントが独断で確認を省くことはしない。

### 見落としやすい振る舞い変更

構造改善のつもりで振る舞いを変えてしまう典型例。差分を出す前に確認する。この表は思い出すための手がかりで、計画にはこの表を写すのではなく、対象の関数・入力・出力・順序・エラー経路に即した具体的な一文を書く（SKILL.md 手順 5）。

| 種類 | 例 |
|---|---|
| 戻り値の型の変化 | `null` を返していたのが `undefined` / 空配列になる。整数が浮動小数点になる。同期関数が Promise を返すようになる |
| 評価順序・初期化順序の変化 | 副作用のある式の取り出し、モジュール移動による読み込み順の変化、静的初期化の順序 |
| 同じ値で意味の違うリテラルの統合 | 「上限 100 件」と「100%」を同じ定数にする |
| 例外 / エラー経路の変化 | 投げる例外の型が変わる、エラーが早く / 遅く出る、握りつぶされていた例外が外に出る（またはその逆） |
| 公開 API・シリアライズ形式の変化 | 関数名・引数順・既定値の変更、JSON のキー名・キー順・数値の書式、DB カラム名、イベント名 |
| その他 | ログ出力の文言や順序（下流が解析している場合）、ソートの安定性、浮動小数点の計算順による丸め差、並行実行時のロック範囲 |

## 4. 停止条件

- 目的の振る舞い変更が「簡単に書ける」状態になったら構造改善をやめ、目的の変更に移る。目安は、変更が 1〜2 か所に収まり、何を書けばよいか迷わない状態。
- まだ気になる箇所が残っていても手を出さない。後回しリストに、場所・理由・想定する手法を 1 行で書く。
- 目的の変更を入れた結果、直後に行うべき改善が見えたら、それも 1 つか 2 つに留める。

## 5. 絡まったときの立て直し

構造改善と振る舞い変更が 1 つのコミットや作業ツリーに混ざってしまったときの選択肢。

| 方法 | 手順 | 向いている場面 | 代償 |
|---|---|---|---|
| そのまま出す | 混在したまま PR を出し、説明欄で構造部分と振る舞い部分を明示する | 差分が小さい。レビュアーが文脈を共有している。急ぎ | レビューで振る舞い変更を見落としやすい。問題が起きたとき一部だけ戻せない |
| 分け直す | `git add -p` で構造部分だけを先にコミットし、残りを振る舞い変更としてコミットする。必要なら一時ブランチに退避して並べ直す | 混在の境界がハンク単位ではっきりしている | 分け直した中間状態でテストが通るか確認する手間。ハンク内で混ざっていると手作業が増える |
| 破棄してやり直す | 利用者の同意を得てから、現在の変更を `git stash push -u -m "<説明>"` または退避ブランチ（例: `git switch -c wip/<名前>` でコミット）に保存し、構造改善から 1 つずつやり直す。最初の試行で得た理解をメモしておく | 混在がひどい。どこまでが何の変更か自分でも説明できない | 書いたコードを捨てる心理的抵抗。ただし 2 回目は理解が進んでいるため速いことが多い |

判断の目安: 説明できるなら分け直す、説明できないなら破棄してやり直す、小さく急ぐならそのまま出して明示する。

### 作業を捨てるときの安全規則

- 「破棄」は退避を意味する。`git reset --hard`、`git checkout -- .`、`git restore .`、`git clean` で変更を消さない。
- 退避の前に利用者の同意を得る。退避先（stash の名前、ブランチ名）を利用者に伝える。
- エージェントが書いていない変更（利用者の未コミットの作業、別作業のファイル）には触れない。`git add -p` や stash の対象から外す。対象を分けられない場合は手を止めて利用者に確認する。
- push 済みのコミットは書き換えない（rebase、amend、reset をしない）。分け直しは新しいブランチや追加コミットで行う。
- force push は利用者の明示的な指示がある場合だけ行う。その場合も `--force-with-lease` を使う。
