# 小さな構造改善の手法

冒頭の 2 つの表（粒度との対応表、原因からの選び方）で手法を選び、選んだ手法の項だけを読む（読む範囲の正本は SKILL.md の「モードと読む範囲」表）。ここに載せるのは、1 つあたり数分〜数十分で終わり（「前に行う」構造改善は合計 1 時間程度が上限の目安）、1 コミットに収まり、振る舞いを変えない改善だけ。例外は M22 の第 1 段階（使用状況の記録の追加）で、外から観測できる出力が増えるため計画では `[振る舞い]`（観測用）として扱う。各項目は「兆候 / 手順 / 落とし穴（振る舞いが変わる危険）/ 次に可能になる改善」で書く。

## 粒度との対応表

| 粒度 | 主に使う手法 |
|---|---|
| 式 | M1 中間値に名前、M2 意味ごとに定数を分ける、M3 条件を述語に |
| 関数 | M4 早期脱出で平らに、M5 関数の抜き出し、M6 不要な間接を畳む、M7 宣言を使用箇所へ寄せる、M8 処理を段階に分ける、M18 読む順に並べ替える |
| ファイル / クラス | M9 名前を実態に合わせる、M10 使われていないものを消す、M11 重複を同じ形に揃えて 1 つにする、M12 一緒に変わるものを近くへ移す、M13 データの塊を型にまとめる、M14 散在する分岐を 1 か所に集める、M18、M21 一緒に変わる要素を小さな単位に切り出す |
| ディレクトリ / パッケージ | M12、M15 暗黙の入力を引数で受け取る、M16 公開面を絞る、M21 |
| リポジトリ / サービス | M17 並行変更（拡張 → 移行 → 縮小）。それ以上は「範囲外の別計画」へ |

M9（名前）、M10（削除）、M19（事情をコメントに残す）、M20（冗長なコメントを消す）、M22（使用状況を記録してから消す）はどの粒度でも使える。M22 は M10 の前段で、未使用だと確信が持てないときに使う。M22 で今行えるのは使用状況の記録を追加することだけ。削除は観測が終わるまで常に後回しリストへ回す（「前に行う」にも「直後に行う」にも入れない）。

診断した原因（structure-and-diagnosis.md の 5 分類）からの選び方:

| 原因 | 手法 |
|---|---|
| 理解しにくい | M1、M4、M5、M8、M9、M18、M19 |
| 変更箇所が散在 | M11、M12、M14、M21 |
| 変更が波及 | M16、M17 |
| インターフェースが使いにくい | M13、M15、M17 |
| ノイズ | M6、M10、M11（揃えるだけ）、M20、M22 |

SKILL.md 手順 4 の D1〜D3 が発火して打ち消しがないときの対応: D1 → M3 または M5 で判定・計算を名前付きの関数に抽出し、呼び出し元ごとに特性テストで現在の振る舞いを固定する（呼び出し元ごとに意味が違うなら関数を分ける）。D2 → M13（既存の型があればそれに寄せる）。D3 → M11 で揃えてから共通部分を M5 で抽出する。

## 式の粒度

### M1 中間値に名前を付ける
- 兆候: 1 行に計算が詰め込まれ、途中の値が何を表すか読み取れない。
- 手順: 部分式をローカル変数に取り出し、意味の名前を付ける。元の式を変数で置き換える。
- 落とし穴: 部分式に副作用や重い処理があり、取り出したことで評価回数や評価順序が変わる（`a() + b()` の `b()` を先に取り出すなど）。短絡評価 `x && f(x)` の右辺を外に出すと、`x` が偽でも `f` が呼ばれる。
- 次に可能: その中間値だけを変える振る舞い変更が 1 行で済む。M5 で関数化しやすくなる。

### M2 意味ごとに定数を分ける
- 兆候: 同じリテラル（`30`, `"active"` など）が複数箇所にあり、どれを直すべきか判断できない。
- 手順: リテラルの各出現について「何を意味しているか」を確認し、意味ごとに別の名前付き定数にする。同じ意味の出現だけを同じ定数に置き換える。
- 落とし穴: 値が同じでも意味が違う出現（「支払期限 30 日」と「セッション 30 分」）を 1 つの定数にまとめると、後でどちらかを変えたときにもう片方も変わる。これは構造改善ではなく将来の振る舞い変更の種になる。
- 次に可能: 業務ルールの数値変更が定数 1 つの変更になる。

### M3 条件を述語に切り出す
- 兆候: `if (user.plan === "pro" && !user.suspended && user.seats > 0)` のような複合条件が何度も現れる。
- 手順: 条件をそのまま返す関数（`canInviteMembers(user)`）を作り、出現箇所を置き換える。中身は一字一句同じにする。
- 落とし穴: 出現箇所ごとに微妙に条件が違う（片方だけ `>=`）のを見落として統一する。統一したいなら、それは振る舞い変更として別コミットにする。
- 次に可能: 条件の変更が 1 か所で済む。M14 の足がかり。

## 関数の粒度

### M4 早期脱出で入れ子を平らにする
- 兆候: 前提条件のチェックで `if` が 3 段以上重なり、本題が右端に追いやられている。
- 手順: 前提を満たさない場合を先に `return` / `continue` / 例外で抜け、本題を左端に戻す。1 条件ずつ変換してテストする。
- 落とし穴: 元のコードで入れ子の外側にあった後処理（ログ出力、`finally` 相当のリソース解放、カウンタ更新）が、早期 `return` で飛ばされるようになる。`else` 側の戻り値が `undefined` / `None` だったことに依存する呼び出し元がある。
- 次に可能: 新しい前提条件を 1 行追加するだけで済む。

例:

```js
// 前
function applyCoupon(order, coupon) {
  if (coupon) {
    if (!coupon.expired) {
      if (order.total >= coupon.minTotal) {
        order.total -= coupon.amount;
      }
    }
  }
  return order;
}
// 後（振る舞いは同じ: どの経路でも order を返す）
function applyCoupon(order, coupon) {
  if (!coupon || coupon.expired) return order;
  if (order.total < coupon.minTotal) return order;
  order.total -= coupon.amount;
  return order;
}
```

### M5 関数を抜き出す
- 兆候: 長い関数の一部に「ここは〜をしている」と説明できるまとまりがある。目的の変更がそのまとまりの中だけで済む。
- 手順: まとまりが読み書きする変数を確認し、読むものは引数、書くものは戻り値にする。抜き出した関数に、何をするかが分かる名前を付ける。
- 落とし穴: 抜き出した範囲で外側の変数を再代入していて、戻り値に含め忘れる。`return` / `break` を含む範囲を抜き出して制御フローが変わる。`this` / レシーバの束縛が変わる。
- 次に可能: 抜き出した関数単位でテスト・差し替え・移動ができる。

### M6 不要な間接を畳む
- 兆候: 中身が 1 行で別関数を呼ぶだけの関数、使い道が 1 つしかない抽象クラスなど、読むたびに飛び先を追う必要がある。
- 手順: 呼び出し元に中身を展開し、元の関数を削除する。利用者が多い・外部公開されている場合は行わない。
- 落とし穴: 間接の層が実は差し替え点（テストのモック、プラグイン）として使われていた。デコレータやアノテーションの効果が失われる。
- 次に可能: 本当に必要な切れ目で M5 をやり直せる。

### M7 宣言を使用箇所へ寄せる
- 兆候: 関数冒頭で変数をまとめて宣言し、使うのは数十行後。
- 手順: 宣言と初期化を、最初に使う直前へ移す。
- 落とし穴: 初期化に副作用がある（現在時刻の取得、乱数、I/O）と、移動で値や実行順が変わる。ループの外から中へ移すと毎回初期化される。
- 次に可能: 関連する行がまとまり、M5 や M8 の範囲が見える。

### M8 処理を段階に分ける
- 兆候: 入力の解釈、計算、出力の整形が 1 関数の中で入り混じっている。
- 手順: 段階の間で受け渡すデータ（中間結果）を決め、前段は中間結果を返すだけ、後段は中間結果だけを受け取るように分ける。
- 落とし穴: 元のコードでは解釈の途中でエラーを返していたのに、分割後は計算まで進んでからエラーになる（エラー経路の変化）。出力の一部を計算途中で書き出していた場合、順序が変わる。
- 次に可能: 入力形式の追加や出力形式の追加が、片方の段階だけの変更になる。

## ファイル / クラスの粒度

### M9 名前を実態に合わせる
- 兆候: 名前と中身がずれている（`getUser` が作成もする、`tmp` が恒久的に使われる）。
- 手順: エディタ / LSP の参照付きリネームを使う。文字列で参照される箇所（リフレクション、設定ファイル、テンプレート）を別途検索する。
- 落とし穴: 公開 API・シリアライズされるフィールド名・DB カラム名・イベント名を変えると、外部から見た振る舞いが変わる。これらは M17 で扱う。
- 次に可能: 正しい名前によって、間違った場所に置かれているコードが見つかる。

### M10 使われていないものを消す
- 兆候: 呼び出し元のない関数、到達しない分岐、コメントアウトされたコード、実態とずれたコメント。
- 手順: 参照検索と履歴で未使用を確かめ、削除する。消したものは履歴から復元できる。
- 落とし穴: 動的呼び出し（名前文字列での呼び出し、DI コンテナ、ルーティング設定）や外部利用者からの呼び出しを見落とす。公開ライブラリの公開関数は未使用に見えても消さない。未使用だと確信できないときは M22 を先に行う。
- 次に可能: 読む量が減り、残ったコードの構造が見えやすくなる。

### M11 重複を同じ形に揃えてから 1 つにする
- 目的: 同じことは同じ書き方にして、書き方の違いが意味の違いだけを表すようにする。そうすると、残った違いを見れば意図的な違いが分かる。
- 兆候: 似ているが少しずつ書き方の違うコードが複数ある。違いが意図的か偶然か分からない。同じ処理なのに、あるファイルは `for` ループ、別のファイルは `filter` / `map` で書かれている。
- 手順: (1) 各コピーを、振る舞いを変えずに同じ書き方へ揃える（変数名、条件の順、ループの形）。(2) 揃えた結果、本当に同じになった部分だけを 1 つにまとめる。(3) 残った差分は引数にするか、意図的な違いとして残す。「揃える」と「統合する」は別のステップで、別のコミットにする。揃えただけで止めてもよい（統合は目的の変更に効くときだけ行う）。
- 落とし穴: 揃える途中で「たぶんこちらが正しい」と片方の挙動に寄せる。それは振る舞い変更。違いが意図的なら M2 と同じく、まとめない。
- 次に可能: 目的の変更が 1 か所で済む。違いが一覧になり、仕様の確認がしやすい。

### M12 一緒に変わるものを近くへ移す
- 兆候: 履歴の同時変更ペアに常に出る 2 ファイル。関数が自分のファイルより別のファイルのデータを多く使っている。あるファイルの中で、1 つの関数だけが周りと一緒に変わらず、別のファイルの要素と一緒に変わっている。
- 手順: 今いる場所の仲間と一緒に変わらない要素を、それと一緒に変わる要素の近く（ファイル・クラス）へ移す。何が一緒に変わるかの情報は不完全なので、一度に大きく動かさず、1 要素 1 コミットで移し、そのたびに次の要素を移すべきか判断し直す。元の場所には一時的に再エクスポートを残して利用者を段階的に移すこともできる。
- 落とし穴: モジュールの読み込み順や初期化順が変わる。循環 import が生まれる。移動先で同名の識別子を上書きする。
- 次に可能: 変更が 1 ファイルに閉じる。M16 で公開面を絞れる。

### M13 データの塊を型にまとめる
- 兆候: 同じ 3〜4 個の引数（`street, city, zip, country`）がいつも一緒に受け渡される。
- 手順: それらを持つ型（構造体、データクラス、レコード）を作り、まず 1 つの関数から引数を置き換える。検証や整形のロジックがあれば後から型へ移す。
- 落とし穴: 可変オブジェクトを共有すると、以前は値渡しだったものが参照共有になり、一方の変更が他方に見える。等価比較やハッシュの挙動が変わる。
- 次に可能: 項目の追加が型の変更 1 か所で済む。関連ロジックの置き場所ができる。

### M14 散在する分岐を 1 か所に集める
- 兆候: 同じ区分（プラン種別、地域、支払方法）での `switch` / `if` 連鎖が複数ファイルにある。区分を 1 つ増やすたびに全部を直す。
- 手順: 区分ごとの値や関数を持つ対応表（マップ）を 1 つ作り、各分岐をその表の参照に置き換える。1 か所ずつ置き換えてコミットする。区分ごとに型を分けるような新しい抽象は導入しない（それは別計画）。
- 落とし穴: 元の分岐の `default` 節の挙動（例外を投げる / 何もしない / 既定値）が表の未登録時の挙動と違う。分岐の評価順に意味があった（先に一致したものが勝つ）。
- 次に可能: 区分の追加が表への 1 行追加になる。

## パッケージ / リポジトリ / サービスの粒度

### M15 暗黙の入力を引数で受け取る
- 兆候: 関数がグローバル変数、シングルトン、環境変数、現在時刻を内部で直接読む。テストで差し替えにくい。
- 手順: 読んでいる値を引数（既定値付き）にし、既存の呼び出し元は既定値で今まで通り動くようにする。その後、呼び出し元を必要に応じて明示的に渡すよう移す。
- 落とし穴: 既定値の評価タイミング（定義時か呼び出し時か）が言語によって違い、時刻などが固定されてしまう。値を読むタイミングが変わり、途中で設定が変わるケースの挙動が変わる。
- 次に可能: テストで入力を固定できる。振る舞い変更の前に特性テストが書ける。

### M16 公開面を絞る
- 兆候: パッケージ内部の型や関数を外部が直接 import している。内部を変えると利用者が壊れる。
- 手順: 外部から実際に使われているものを洗い出し、入口（index / `__init__` / 公開モジュール）経由に集約する。内部専用のものは非公開にする。利用者の import 書き換えは 1 利用者 1 コミットで進める。
- 落とし穴: 別リポジトリ・別サービスからの利用を見落とす。非公開化はそれ自体が公開 API の変更になる。
- 次に可能: 内部の変更がパッケージ内で閉じる。

### M17 並行変更（拡張 → 移行 → 縮小）
- 兆候: 関数シグネチャ、API、メッセージ形式、DB カラムなど、複数の利用者が同時に依存しているものを変えたい。
- 手順: (1) 拡張: 新しい形を古い形と並べて追加する。新しい入口の中身は既存実装に委譲する。(2) 移行: 利用者を 1 つずつ新しい形に移す。(3) 縮小: 利用者がいなくなったことを確認してから古い形を消す。各段階は単独でリリースでき、どこで止めても動く。
- 落とし穴: 拡張段階で新旧の入口の挙動を微妙に変えてしまう。縮小を忘れて二重管理が残る（後回しリストに必ず載せる）。データ形式の場合、新旧両方を読み書きできる期間が必要。
- 次に可能: 一斉変更なしに、利用者ごとのペースで切り替えられる。

## 追加の手法（読みやすさ、コメント、凝集、削除の前段）

### M18 読む順に並べ替える
- 兆候: ファイル内の関数や定義が追加された順に並んでおり、入口の関数が末尾にある。呼び出し元と呼び出し先が離れていて、読むたびに上下を行き来する。
- 手順: 読み手が最初に必要とするもの（公開される入口、主な流れ）を上に、詳細（補助関数、定数の細目）を下に置く。または、互いに参照し合う定義を隣り合わせにする。並べ替えだけを 1 コミットにし、他の改善と同じコミットに混ぜない（差分が移動で埋まり、混ぜた変更がレビューで見えなくなる）。
- 落とし穴: 宣言順が意味を持つ言語や仕組みがある。モジュールのトップレベルが上から実行される言語（定義前の参照、デコレータによる登録順）、宣言前に使えない `const` / `class`、前方宣言が必要な言語、上書き順で結果が決まるもの（スタイルシート、設定のマージ、ルーティングの一致順）、マイグレーションの適用順。これらでは並べ替えが振る舞い変更になる。
- 次に可能: 目的の変更で読む範囲が上から順にたどれる。M5 や M21 の対象が見つけやすくなる。

### M19 コードから読み取れない事情だけを短いコメントに残す
- 兆候: 理解に時間がかかった箇所で、その理由がコードに現れていない（外部サービスの仕様上の制約、過去の障害を避けるための順序、意図的に効率の悪い書き方をしている理由）。
- 手順: (1) まず、その事情を名前・定数・関数に移せないか考える（M1、M2、M3、M5、M9）。例: `sleep(2)` に「受付 API が 1 秒以内の再送を重複扱いするため」とコメントするより、`RETRY_GAP_FOR_DEDUP_WINDOW = 2` という定数にする。(2) 移せない「なぜ」だけを 1〜2 行で書く。「何をしているか」はコードに任せる。
- 落とし穴: 推測を事実のように書く。確かめていないなら「（未確認）」と書くか、書かない。ドキュメント生成に使われるコメントや、実行されるコメント（docstring 内のテスト例など）を変えると、生成物やテスト結果が変わる。コメント追加もコード変更と同じコミットに混ぜない。
- 次に可能: 次に読む人が同じ調査を繰り返さずに済む。

### M20 コードと同じことを言うだけのコメントを消す
- 兆候: `count += 1  # count を 1 増やす` のように、コードを言い換えただけのコメント。M5 や M9 の結果、関数名がコメントと同じ内容を表すようになり、コメントが冗長になった。
- 手順: コードを読めば完全に分かることだけを言っているコメントを消す。理由・制約・単位・前提など、少しでもコードにない情報を含むなら消さない（その情報を名前へ移せるなら移してから消す）。
- 落とし穴: コメントに見えて意味を持つ記述を消す（リンタ・型検査の抑止指示、ビルドタグ、コンパイラへの指示、文字コード宣言、ライセンス表記、コード生成のマーカー）。これらは消さない。
- 次に可能: 残ったコメントが「読む価値のあるもの」だけになり、M19 で書いたコメントが埋もれない。

### M21 一緒に変わる要素を小さな単位に切り出す
- 兆候: 大きなファイルやクラスの中で、ある種類の変更のたびに決まった数個の関数・定数だけが一緒に変わる（履歴の同時変更や、目的の変更で触る要素の一覧から分かる）。残りの要素はその変更では変わらない。
- 手順: 一緒に変わる要素群の置き場所として新しいファイル（小さなモジュール）を作り、要素を 1 つずつ移す。1 要素 1 コミットにし、移すたびに「次の要素も本当に一緒に変わるか」を判断し直す。元の場所からは再エクスポートで参照を保つ。新しいインターフェースや基底クラスは作らない（それは範囲外の別計画）。
- 落とし穴: 循環 import、モジュールの初期化順の変化。一度に多くを移して、実は一緒に変わらない要素まで連れてくる。
- 次に可能: その種類の変更が新しい小さな単位の中で閉じる。M16 でその単位の公開面を絞れる。

### M22 使われているか確信が持てないものは、使用状況を記録してから消す
- 兆候: 参照検索では呼び出し元が見つからないが、動的呼び出し、外部利用者、まれにしか動かない経路（月次バッチ、障害時の手順）の可能性を否定できない。
- 手順: (1) 対象の入口に使用状況の記録（ログ 1 行、メトリクスのカウンタ）を入れる。計画ラベルは `[振る舞い]`（観測用）。記録は外から観測できる出力が増えるので、構造改善とは別のコミット・PR にする。(2) 対象が動きうる周期をすべて含む期間（月次処理があるなら 1 か月以上）観測する。(3) 記録がゼロなら M10 で削除し、記録コードも一緒に消す。使われていたら、呼び出し元を M19 でコメントに残して削除をやめる。
- 落とし穴: 記録が性能やログ量に影響する（頻繁に呼ばれる経路では間引く）。観測期間が短く、まれな経路を見逃す。記録コードを消し忘れる（後回しリストに載せる）。
- 次に可能: 根拠を持って削除できる。

## 小さな構造改善の範囲を超えるもの

次は 1 コミットで終わらず、設計判断を伴うため、目的の変更の前準備として混ぜない。計画テンプレートの「範囲外の別計画」に書く。

- 新しい抽象の導入（インターフェース、基底クラス、戦略の差し替え機構）
- モジュール / パッケージの分割・統合
- サービスの分割・統合、データストアの分離

これらを入れる場合も、元に戻せる段階に分ける。

1. 切替点を 1 つ作る: 呼び出し元と実装の間に、どちらの実装を使うかを決める 1 か所（関数、ファクトリ、設定フラグ）を置く。この時点では旧実装しかつながっていない。
2. 新実装を並べる: 新しい抽象・モジュール・サービスを、旧実装と並べて追加する。切替点はまだ旧実装を向いている。
3. 少しずつ向きを変える: 利用者の一部、リクエストの一部、機能の一部から新実装へ切り替える。比較のため両方を実行して結果を照合する期間を設けてもよい。
4. 戻せることを確認しておく: 切り替えはフラグや設定 1 つで戻せる状態を保つ。データ形式を変える場合は旧形式でも読める期間を設ける。
5. 旧実装を消す: すべての利用者が移り、一定期間問題がないことを確認してから削除する。

各段階を別 PR にし、どの段階で止めてもシステムが動くことを条件にする。
