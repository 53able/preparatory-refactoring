# レビューモード

構造改善と振る舞い変更が混ざった差分・PR を受け取ったときに読む（読む範囲の正本は SKILL.md の「モードと読む範囲」表）。

## 手順

1. 差分を取得する。PR なら `gh pr diff <番号>`、ブランチなら `git diff <base>...<head>`、コミット列なら `git log -p <base>..<head>`。
2. PR の説明・コミットメッセージ・関連 issue から、目的の振る舞い変更を一文で特定する。書かれていなければ差分から推定し、推定であることを明記する。
3. ハンクごとに分類し（下の「分類の基準」）、「構造と判定した根拠」列を必ず埋める。1 つのハンクに両方が混ざる場合は「混在」とし、どの行がどちらかを書く。
4. 親コミットと読み取りだけで比較する（下の「親コミットとの比較」）。
5. 構造改善のハンクについて、目的の変更に寄与しているかを判定する。
6. 構造改善とされているハンクに紛れ込んだ振る舞い変更を探す（timing-and-discipline.md の「見落としやすい振る舞い変更」を照合表として使う）。
7. 兄弟箇所を検索する（下の「兄弟箇所」）。
8. 分割案を順序つきで出す。PR 単位だけでなく、各 PR の中のコミットまで分ける。
   - 構造改善の PR の中も 1 コミット 1 改善にする。抽出・移動・改名・定数化・fixture 追加は、種類ごとに別コミットにする。同じファイルへの変更でも、種類が違えば分ける。同じ種類でも対象が別々（2 つの関数をそれぞれ抜き出す）なら別コミットにする。
   - 純粋な移動・改名・抽出は、修正（振る舞い変更）のコミットに含めず、それぞれ独立したコミットにする。helper の抽出を修正コミットに含めない。
   - コメント・docstring だけの変更と、空白・インデントだけの変更（ラッパー要素で囲んだことによる再インデントを含む）は、それぞれ独立した構造コミットにする。修正のコミットに含めない。
   - 呼び出し側の書き換えを伴う未使用引数の削除（残る引数の順序を保つもの）と、ロジックを変えない式の移動も、修正とは別のコミットにする。
   - 生成物（スキーマから生成されるファイル、ロックファイル、翻訳の生成結果など）は、それを生み出す元の変更と同じコミットに入れる。元の変更から切り離さない。
   - 分割案はレビュー対象の差分にある変更だけを並べ替える。差分にない構造改善は分割案に入れず、提案するなら分割案の外の「追加の提案」に書く。
   - diff に構造編集が 1 つでもあれば「構造 PR 不要」とは書かず、最小 1 コミットの構造コミットに分ける。
9. 構造改善 PR ごとに、次の変更が何か所・どの程度で済むようになるかを書いた説明文案を出す（出力形式の末尾）。

### 分割案の確認

出力前に、分割案の各コミットについて次を確かめる。結果は出力形式の「分割案の確認表」に書く。

- 確認表で各コミットの「種類」を 1 つだけ書けるか。種類は構造の種類名 1 つ（抽出、移動、改名、定数化、早期 return 化、fixture 追加、特性テスト追加、コメント、空白、未使用引数の削除、式の移動など）か「振る舞い」。2 つ以上書きたくなるコミットは分ける。生成物は元の変更と同じ種類として数える。
- コミットの説明を 1 つの動詞句で書けるか（「A を定数化し、B を抜き出す」のように「〜し、」でつながるなら分ける）。
- そのコミットだけを適用した状態でテストが通るか（確認方法を書く。レビューモードでは自分で実行しない）。
- 純粋な移動・改名・抽出、helper の抽出が、修正や機能追加のコミットに含まれていないか。含まれていれば、それだけのコミットを先に切り出す（移動と修正が同じコミットにあると、差分が「全行削除・全行追加」に見え、修正部分を確認できない）。
- 抽出・移動・改名・定数化・fixture 追加のうち、2 種類以上が 1 コミットに入っていないか。
- コメント・docstring、空白・再インデント、未使用引数の削除、式の移動が、修正のコミットに入っていないか。
- 生成物が、それを生み出す元の変更と別のコミットになっていないか。
- 差分にない変更（新しい構造改善）が分割案に入っていないか。入っていれば「追加の提案」へ移す。
- diff に構造編集があるのに「構造 PR 不要」「構造コミットなし」と書いていないか。
- 構造改善のコミットに、目的の変更のどこを楽にするか、または目的の変更で触った箇所への次の変更（予定または高頻度）のどこを楽にするかを一文で添えられるか。添えられないコミットは「目的に寄与しない構造改善」に移す。

## 分類の基準

| 分類 | 定義 | 例 |
|---|---|---|
| 構造 | 外から観測できる振る舞い（戻り値、副作用、例外、出力、公開 API、利用者が依存している性能特性）を変えない。SKILL.md の定義と同じ | 名前変更（内部）、関数の抜き出し、ファイル移動、未使用コードの削除 |
| 振る舞い | 上記のいずれかを変える | 条件の追加、計算式の変更、新しい API、エラーメッセージの変更 |
| 混在 | 1 ハンクに両方がある | 関数を抜き出しつつ条件を 1 つ足している |
| テスト | テストコードのみ | 特性テストの追加、既存テストの更新 |
| その他 | 設定、依存更新、生成物 | lock ファイル、CI 設定 |

移動・抽出・改名に見えても、次のどれかが変わっていれば「振る舞い」（一部なら「混在」）に分類し、変化した行を示す。変わっていない純粋な移動は「構造」のまま。

- 並行性: ロックの範囲、トランザクションの範囲（抽出した関数の中でロックを取り直す、トランザクションの外へ処理が出る）
- ユーザーに見える文字列・メッセージ（文言、句読点、プレースホルダの順）
- UI の順序・フォーカス（項目の並び、タブ順、初期フォーカス）
- 公開スキーマ・列の値・範囲・順序（API のフィールド、CSV の列順、enum の値、値の範囲）

テストの期待値が変わっているハンクは、対応する実装側の変更が振る舞い変更であることの強い証拠になる。構造改善だけのはずなのにテストの期待値が変わっていたら、必ず指摘する。

## 親コミットとの比較（読み取りのみ）

- 対象: diff に含まれるファイルのうち、テスト・メッセージ文字列・設定のファイルに限り、最大 10 パス。
- 方法: パスごとに `git -C <repo> show <commit>^:<path>`（親での内容）と `git -C <repo> diff <commit>^ <commit> -- <path>`（増減）を読む。`<commit>` は対象コミット（コミット列なら各コミット）。
- テストやビルドは実行しない（第三者のコードを実行しない）。
- 結果は「親コミットとの比較」表に書く: パス、種類（テスト / メッセージ / 設定）、増えたもの、減ったもの、変わったもの、分類への影響。テストケースの削除や期待値の変更、メッセージの文言変更、設定の既定値変更は、対応するハンクを「振る舞い」に寄せる根拠になる。

## 兄弟箇所

- 変更されたパターン（例: 価格の丸めを `Math.round` から `roundYen()` に置き換えた）について、まだ適用されていない同種の箇所をリポジトリで 1 回検索する（例: `rg -n 'Math\.round\(.*price' src/`）。
- ヒットのうち最大 10 件を確認し、「適用済み / 未適用（同じ意味）/ 未適用（意図的に別）」を結果に書く。未適用で同じ意味の箇所は、この PR の範囲に入れるか後回しにするかを指摘する。

```markdown

- 悪い例: 差分にない「shipping.js の料金表を定数に寄せる」を分割案のコミットに入れる。差分にない改善は「追加の提案」に書く。
```

構造の価値は機能と違って外から見えにくい。構造改善の PR には、上のように「次の変更が何か所・どの程度で済むようになるか」を具体的に書いた説明文案を必ず付ける。元の PR 説明にこれが無ければ、レビュー結果の指摘として挙げる。

## 判断に迷う場合

- 性能が変わるだけの変更: 利用者が依存している性能特性（タイムアウトに関わる処理時間、メモリ上限）に影響しうるなら振る舞い扱いにし、理由を書く。影響しないなら構造扱い。
- ログ文言の変更: ユーザーに見えず、下流で解析されていなければ構造扱いでよいが、解析の有無を確認する問いとして指摘する。ユーザーに見えるメッセージは常に振る舞い。
- 内部関数のシグネチャ変更: 呼び出し元が同じ PR 内ですべて更新されていれば構造。外部パッケージから呼ばれうるなら振る舞い。
