# 構造の把握と変更しにくさの診断

SKILL.md の手順 2〜3 で読む。計画・実行モードで必読なのは「0. 事実確認」と「4. 原因の分類」だけ。1〜2 は粒度・依存の判定に迷ったとき、3 はスクリプトを使うときに読む。バックログモードは 3・4 節が必読。

## 0. 事実確認

前提の事実を SKILL.md 手順 2a の「事実確認表」に 1 主張 1 行で書く。本文は「事実 #n より」で参照し、表に無い事実は書かない。

| 種別 | 確かめること | 「確認済」にできる条件 |
|---|---|---|
| 存在 | 目的の変更に関わる機能・設定・関数・フラグがすでにないか。言い換え、略語、別の層（設定、環境変数、DB、フラグ、別サービス）も探す | 検索コマンドと結果。名前で登録されるもの（ツール名、コマンド名、設定キー、イベント名、ルート）は識別子と実行時の文字列リテラルの両方で検索 |
| 否定 | 「存在しない」「呼ばれていない」「登録されていない」「効いていない」 | 検索コマンドと 0 件の結果。動的参照（文字列でのディスパッチ、設定からの登録）の可能性が残るなら「未確認」 |
| 肯定 | 「検査される」「効いている」「対応済み」 | 経路表で、すべての呼び出し元について対象項目が渡されているかを確認した。1 つでも未確認なら「未確認」とし、本文には「検査関数は存在するが、経路は未確認」とだけ書く |
| 経路 | 入口（画面・API・ジョブ）→ 取得・計算・保存 → 出力 | 各段の file:line。別経路の同じ計算（見積もりと確定、画面と CSV）、既存の制御（上限、キャッシュ、フラグ）、出力の後段（メール、PDF）を含める |

例 1（肯定の主張。1 行目は事実確認表、2 行目は経路表の行。一部の経路で検査が走らないと分かる）:

```
| 3 | 郵便番号は validateAddress で検査される | 肯定 | src/validate.js:20 | orders 経路では検査されない | 確認済 |
| 3 | src/validate.js:20 | src/api/orders.js:61, src/admin/import.js:88 | orders.js:61 は { street, city } のみ（zip なし）/ import.js:88 は addr 全体 |
```

例 2（名前で登録されるものの否定。識別子と登録名を 1 コマンドで検索。セル内の `|` は `\|`）:

```
| 1 | web_search ツールは未登録 | 否定 | rg -n 'WebSearchTool\|"web_search"' → src/tools/web.ts:5 のみ（"web_search" は 0 件） | 定義のみ。登録名の参照なし | 確認済 |
```

## 1. 粒度ごとの「閉じているか」判定

目的の変更で触る要素を列挙し、下の表の各行で「この粒度の 1 単位の中で変更が完結するか」を判定する。完結しない最小の粒度が、構造改善の主戦場になる。

| 粒度 | 閉じている状態 | 閉じていない兆候 |
|---|---|---|
| 式 | 1 つの式を書き換えれば済む | 同じ計算が式の中で複数回、意味の違う値が同じリテラル |
| 関数 | 1 関数の中で済む | 関数の前半と後半を両方直す必要、呼び出し側でも同じ判定をしている |
| ファイル / クラス | 1 ファイルで済む | 同じ分岐（例: 会員種別ごとの `switch`）が複数ファイルにある |
| ディレクトリ / パッケージ | 1 パッケージで済む | 内部の型や関数を外のパッケージが直接参照している |
| リポジトリ | 1 リポジトリ・1 回のリリースで済む | 共有ライブラリと利用側を同時に更新しないと壊れる |
| サービス | 1 サービスのデプロイで済む | API・メッセージ形式・DB スキーマを複数サービスで揃えて出す必要 |

記録例（配送料計算に「離島追加料金」を足す場合）:

```
式:       閉じない — 料金の上限 5000 が 3 か所に直書き
関数:     閉じない — calcShipping と estimateAtCart が同じ地域判定を別々に持つ
ファイル: 閉じない — 地域判定が shipping.js と cart.js に重複
パッケージ: 閉じている
サービス:   閉じない — 請求サービスが料金内訳の JSON 形式を前提にしている
```

## 2. 依存の洗い出し

### 静的に見える依存

コードを読む・検索すれば見つかるもの。種類ごとに grep の起点が違うので分けて調べる。

- 呼び出し（関数・メソッド・HTTP / RPC）
- import / require / モジュール参照
- イベントの発行と購読（イベント名の文字列で結ばれる）
- 共有データ（同じテーブル、同じキャッシュキー、同じファイル）
- 設定値（同じ環境変数や設定キーを複数箇所が読む）
- スキーマ（DB スキーマ、型定義、OpenAPI などのコード生成元）
- メッセージ形式（キューに流す JSON、ログ形式を解析する下流ツール）

### 暗黙の依存

検索では見つかりにくく、壊してから気づくもの。

- 前提としている順序（初期化順、呼び出し順、リストの並び順）
- 値の意味の取り決め（`0` は「未設定」、`-1` は「無制限」など）
- 時刻・タイムゾーン・ロケール・丸め方の前提
- 外部の利用者（別チームのスクリプト、BI のクエリ、手作業の運用手順）
- 性能特性に依存した挙動（タイムアウト値、バッチサイズ）
- 同じ知識の重複（同じ業務ルールが別言語・別サービスで二重実装）

### 結合は「どの変更に対して連動するか」で書く

「A と B は密結合」だけの指摘は不可。必ず変更の種類を添える。

- 良い: 「料金区分を 1 つ増やすと、`shipping.js` の判定と `cart.js` の判定と請求サービスの内訳スキーマが同時に変わる」
- 良い: 「ログ形式の項目名を変えると、監視ダッシュボードのクエリが壊れる。項目追加では壊れない」
- 不可: 「shipping と cart は結合度が高い」

同じ 2 要素でも、変更の種類によって連動したりしなかったりする。連動しない変更については結合していないとみなしてよい。

### 波及の形

- 一対多: 1 か所の変更で、直接の利用者 N 個が同時に変わる。利用者を数えれば規模が分かる。
- 連鎖: 変更が利用者に伝わり、その利用者の変更がさらに先へ伝わる。規模は事前に読みにくく、見積もりの誤差が大きい。連鎖の途中に「ここで止まる」境界（変換層、安定したインターフェース）を作ることが優先度の高い改善になる。

記録時は「A → B, C, D（一対多）」「A → B → E → 請求サービス（連鎖）」のように矢印で書く。

## 3. 変更履歴で結合を実測する

静的解析で見えない結合は、履歴の同時変更に現れることが多い。同梱スクリプトで測る。

```bash
uv run "$SKILL_DIR/scripts/change_coupling.py" --repo . --since "12 months ago"
uv run "$SKILL_DIR/scripts/change_coupling.py" --repo . --path src/shipping/ --path src/cart/ --format json
uv run "$SKILL_DIR/scripts/change_coupling.py" --repo . --partner src/shipping/fee.py --top 10
```

`SKILL_DIR` はこのスキルのディレクトリ（SKILL.md がある場所。このファイルの 1 つ上）を指す。

主なオプション:

| オプション | 意味 | 既定 |
|---|---|---|
| `--since` / `--until` | 期間（git log と同じ書式） | なし |
| `--path` | パスで絞る（複数可、先頭の `./` と `/` は除去）。末尾が `/` なら接頭辞一致、それ以外は完全一致または `<PATH>/` 配下（`src` は `src2/` に一致しない） | なし |
| `--max-files` | これを超えるファイル数のコミットを一括変更として除外（2〜500。判定は `--path` 絞り込み前の全ファイル数） | 30 |
| `--min-pair-count` | ペアとして出す最小同時変更回数（1 以上） | 2 |
| `--top` | 一覧の件数（0 以上、0 で無制限） | 20 |
| `--warn-below` | 分析コミット数がこれ未満なら警告（0 以上） | 30 |
| `--partner` | このファイル（最終的なパスで完全一致、複数可）を変えたコミットで一緒に変わったファイルを、回数と割合（同時変更回数 ÷ 指定ファイルの変更回数）で出す。`--since` / `--until` / `--max-files` / `--top` を同じ意味で使い、相手は `--path` に一致するものだけ。`--min-pair-count` は使わない。text 出力ではホットスポットとペアを省略する（json の `partners` に入る） | なし |
| `--format` | `text` または `json` | text |

- リネームは古いコミットから順に追跡し、旧パスの履歴を新パスに付け替える（`renames_followed` に件数）。集計は最終的なパスで行う。削除後に同じパスで作り直したファイルは同じパスとして合算される。
- 並行ブランチの片方でリネームし、もう片方で旧パスを変更していた場合、旧パス側の履歴は付け替えられず別の行として残る。
- ファイル名は NUL 区切りで読むので、空白・引用符・タブ・非 ASCII を含む名前もそのまま扱える。UTF-8 でないファイル名は `\x..` 形式で表示される。
- 利用者の git 設定（ページャ、外部 diff、textconv、署名表示、相対パス表示、リネーム検出の上限）や `GIT_DIR` などの環境変数の影響を受けないよう、設定を上書きして実行する。bare リポジトリも対象にできる。
- 空コミット（ファイル変更なし）は `commits_empty` に数え、`commits_seen` には含めない。
- リネーム検出が上限で省略された場合は警告に出る。
- 範囲外の値を渡すと終了コード 2 で止まる。

読み方:

- hotspots: 変更回数が多いファイル。改善の効果が回収されやすい場所。
- pairs: `together` が同時変更回数、`P(b|a)` は「a を変えたとき b も変えた割合」。`P(b|a)` が高く `P(a|b)` が低い場合は、a を変えると b も直す必要がある。b が a の内部を知っている（b が a に依存している）可能性が高い。逆に b だけを変えるときは a に影響しにくい。
- 静的依存がないのに同時変更が多いペアは暗黙の依存の候補。前節の暗黙の依存リストに照らして理由を探す。
- partner: `ratio` は「指定ファイルを変えたとき、その相手も変えた割合」。経路の追跡で出てこないのに割合が高い相手は、着地点の漏れ（設定、スキーマ、別経路の同じ計算）の候補。指定ファイルの変更回数が `--warn-below` 未満なら警告が出る。0 回なら最終的なパス（リネーム後の名前）と期間を見直す。
- テストファイルと実装ファイルのペアは健全な同時変更なので除外して読む。
- 警告が出たら割合を根拠にせず、方向の参考に留める。
- 一括整形のコミットを除外しきれないときは `--max-files` を下げる。逆に正規の大きな変更まで除外していないか、`skipped_bulk` の件数を確認する。

エラー時は終了コード 2 と理由が出る（git が無い、リポジトリでない、履歴が空）。

## 4. 原因の分類

目的の変更が高くつく理由を、次の 5 つから選ぶ（複数可）。分類しないまま手法を選ばない。

| 原因 | 典型的な兆候 | 効く改善の方向 |
|---|---|---|
| 理解しにくい | 読んでも何をしているか確信できない。名前と中身がずれている。深い入れ子 | 名前の修正、中間値への命名、入れ子を平らに、段階への分割、読む順への並べ替え、コードから読み取れない事情だけを短いコメントに残す |
| 変更箇所が散在 | 1 つの業務ルールを直すのに複数ファイルを直す（履歴の同時変更ペアに出る） | 重複を同じ形に揃えて 1 か所に集める、一緒に変わらない要素を一緒に変わる相手の近くへ移す、一緒に変わる要素を小さな単位に切り出す、散在する分岐を表に集約する（移動は 1 要素ずつ） |
| 変更が波及 | 1 か所直すと利用者や下流が連鎖して壊れる | 公開面を絞る、変換層で止める、並行変更で段階的に切り替える |
| インターフェースが使いにくい | 呼び出しのたびに同じ前処理を書く。引数の順番を間違えやすい。隠れた前提がある | 使いやすい入口を足して内部は既存へ委譲、データの塊を型にまとめる、暗黙の入力を引数に |
| ノイズ | 使われていないコード、古いコメント、同じことの書き方が不揃い、コードを言い換えただけのコメント | 未使用コードの削除（確信がなければ使用状況を記録して観測してから）、コードと同じことを言うだけのコメントの削除、書き方を揃える（揃えることと統合することは別コミット） |

分類の結果は計画テンプレートの「診断」欄に、根拠（ファイル名、関数名、履歴の数値）と一緒に書く。具体的な手法は `techniques.md` の「診断した原因からの選び方」表から選ぶ。
