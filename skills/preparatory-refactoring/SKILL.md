# preparatory-refactoring

振る舞い変更を安く・安全に入れるために、必要な分だけ構造を整える。整えること自体を目的にしない。構造改善が要らないと判断することも正当な結論である。

## 前提となる区別

- 構造改善: 外から観測できる振る舞い（戻り値、副作用、例外、出力、公開 API、利用者が依存している性能特性）を変えない変更。振る舞い変更: そのいずれかを変える変更（機能追加、不具合修正、仕様変更）。
- 両者は原則として別コミット・別 PR にする。混ざったときは `references/timing-and-discipline.md` の「絡まったときの立て直し」に従う。`SKILL_DIR` は、この SKILL.md があるディレクトリを指す。実行前に絶対パスへ置き換える。

## モードと読む範囲

参照ファイルは「必読」だけを読み、「必要なときだけ」は条件に当てはまったときに該当節だけを読む。この表が読む範囲の正本。

| モード | 依頼の例 | コード変更 | 手順 | 必読 | 必要なときだけ |
|---|---|---|---|---|---|
| 計画 | 「X を追加したい。先に整理すべき？」 | しない | 1〜5、テンプレートで出力 | SKILL.md、structure-and-diagnosis.md の「事実確認」「原因の分類」節 | techniques.md: 冒頭の表と選んだ手法の項だけ / structure-and-diagnosis.md の他の節: 粒度・依存の判定に迷う、スクリプトを使う / timing-and-discipline.md: タイミング判断に迷う / principles.md: 利用者に理由を説明する |
| 実行 | 「X を実装して。必要なら整理も」 | する | 1〜6 | 計画モードの必読、timing-and-discipline.md の「実行の規律」節 | 計画モードと同じ。混ざったら timing-and-discipline.md「絡まったときの立て直し」 |
| レビュー | 「この PR / diff を見て」 | しない | review-mode.md（ハンクごとに構造と判定した根拠を書く。親コミットと読み取りだけで比較（最大 10 パス、実行しない）。抽出・移動・改名・定数化・fixture 追加・コメント・空白は種類ごとに別コミット、生成物は元の変更と同じコミット、差分にない改善は分割案に入れない。兄弟箇所を 1 回検索） | SKILL.md の「前提となる区別」、review-mode.md、timing-and-discipline.md の「見落としやすい振る舞い変更」 | timing-and-discipline.md「絡まったときの立て直し」: 分け直し方を示すとき |
| バックログ | 「技術的負債をどこから返すべき？」 | しない | バックログ手順 | SKILL.md、structure-and-diagnosis.md の「変更履歴で結合を実測する」「原因の分類」節 | techniques.md: 冒頭の表と推奨する手法の項だけ |

## 作業量の目安（計画・実行モード）

- 検索は目的の変更の経路上に限り、1 主張 1 コマンドにする（存在の主張は `rg -n 'Ident|"literal"'` のように識別子と文字列リテラルを 1 回で検索。表のセルでは `|` を `\|` と書く）。計画本文は `[構造]` 項目 5 個以内、全体 120 行以内。構造メモの各欄は 1 行（表を除く）。

## 手順 1: 対象の振る舞い変更を一文で定義する

「<誰 / 何> が <条件> のとき <新しい振る舞い> になるようにする」の形で書く（例: 「離島の配送先を含む注文で、配送料に 800 円を加算する」）。一文にできなければ利用者に確認する。具体的な振る舞い変更がないならバックログモードへ。

## 手順 2: 事実を確かめ、構造を把握する

### 2a. 事実確認表を作る（必ず行う）
前提となる事実を、テンプレートの「事実確認表」に 1 主張 1 行で書く。本文（診断・計画）は「事実 #3 より」のように行番号で参照し、表に無い事実は本文に書かない。詳細と例は structure-and-diagnosis.md「0. 事実確認」。

- 列: `# | 主張 | 種別 | 確認したもの（検索コマンドまたは file:line） | 結果 | 判定（確認済 / 未確認）`
- 種別「存在」: 関わる機能・設定・関数・フラグがすでにないか。名前で登録されるもの（ツール名、コマンド名、設定キー、イベント名、ルート）は識別子と実行時の文字列リテラル（例: `"web_search"`）の両方で検索する。
- 種別「否定」: 「存在しない」「呼ばれていない」「登録されていない」「効いていない」。検索コマンドと結果を必ず書く。
- 種別「肯定」: 「検査される」「効いている」「対応済み」。経路表に `検査箇所 file:line | 呼び出し元 file:line（すべて列挙） | その呼び出しで対象項目が渡されているか（引数名と行）` の行を必ず追加する。呼び出し元を 1 つでも確認していなければ判定は「未確認」とし、本文には「検査関数は存在するが、経路は未確認」とだけ書く。
- 種別「経路」: 目的の変更が通る経路を入口から取得・計算・保存・出力まで一度たどる。別経路の同じ計算や既存の制御（上限、フラグ）を見落とさない。
- 着地点: 経路上のファイルを、呼び出し元・呼び出し先へ 1 段ずつ広げて列挙し、各ファイルを「変更する / 変更不要（理由と事実 #n）」に分類して着地点表に書く。中心のファイルは 2c の `--partner` で履歴上の相手も加える。

### 2b. 構造の把握
- 触る要素（ファイル、関数、型、設定、スキーマ、外部 API）を列挙する。
- 式 / 関数 / ファイル・クラス / パッケージ / リポジトリ / サービスの各粒度で変更が閉じるかを判定し、閉じない最小の粒度を特定する。
- 依存を静的依存（呼び出し、import、イベント、共有データ、設定、スキーマ、メッセージ形式）と暗黙の依存（順序の前提、値の意味、外部利用者、重複した業務ルール）に分ける。
- 結合は必ず「どの種類の変更に対して連動するか」で書き、波及が一対多か連鎖的かを区別する。

### 2c. 変更履歴で実測する（git リポジトリなら結論に関係なく必ず）
- `uv run "$SKILL_DIR/scripts/change_coupling.py" --repo . --path <対象ディレクトリ>/ --top 15`（他のオプションは `--help`）。自己テスト: `uv run "$SKILL_DIR/scripts/test_change_coupling.py"`
- 結果は構造メモの「履歴」欄に必ず書く。「構造改善なし」を省略の理由にしない。警告が出たら割合は方向の参考に留める。静的依存のない同時変更ペアは暗黙の依存の候補。エラー（終了コード 2）なら静的調査だけで進めたと書く。
- 着地点の中心となるファイル（最大 3 つ）ごとに `--partner <file> --top 10` を付けて実行し（`--path` は付けない）、割合 0.3 以上かつ 2 回以上の相手を着地点表に加えて「変更する / 変更不要（理由と事実 #n）」に分類する（出所: 経路 / 履歴 / 両方）。指定ファイルの変更が 10 回未満なら「履歴不足（n 回）」と書いて飛ばしてよい。10 回以上あるのに使わないなら理由を書く。履歴の数値を判断に使った箇所（着地点の追加・除外、候補の優先度）を少なくとも 1 つ、種別「履歴」で事実確認表に載せ、「履歴」欄から事実 #n で参照する。

### 2d. D 判定の入力を記録する
- 目的の変更で書き換える判定・計算ごとに、本番コードの呼び出し元と類似箇所を `rg` で 1 回検索し、件数と `file:line` を書く。その変更が既存の式を書き換えるか、追加のみかを 1 行で書く。
- 引数を足す関数ごとに、現在の引数の数を書く。lint / 型検査の設定ファイルの有無と、関連する閾値（設定値、なければツールの既定値）を 1 行で書く。

## 手順 3: 変更しにくさの原因を診断する

原因（理解しにくい / 変更箇所が散在 / 変更が波及 / インターフェースが使いにくい / ノイズ）を選び（複数可）、根拠を事実 #n か履歴の数値で示す。原因ごとの改善の方向は structure-and-diagnosis.md「4. 原因の分類」、手法の番号は techniques.md（M1〜M22）。どの原因にも当てはまらなくても、手順 4 の D1〜D3 は必ず判定する。

## 手順 4: タイミングを判断する

各候補を「前に行う / 直後に行う / 後回しリストに記録 / 行わない」から選ぶ。「直後」は目的の変更で触った箇所への次の変更（予定がある、または履歴上よく変わる）を楽にする改善に限る。触っていない箇所や次の変更を言えないものは「後回し」。判断材料（向きが分かればよい）:

1. 「改善の手間 + 改善後の変更の手間」と「改善なしの変更の手間」の大小。後続の変更で回収できるか（ホットスポットか）
2. 改善が今の理解に効くか。何をどう直せばよいか分かっているか。後回しにすると高くつくか（文脈を忘れる、衝突する）
3. 早く届けることと将来の変更余地を残すことのどちらを優先するか
4. 「結合したまま変更する費用」と「結合を解く費用」の比較。ある種類の変更への結合を減らすと別の種類への結合や間接が増えることがある。結合を限界まで減らそうとしない
5. 広がる決定か（ID の型、日時の表現、共通ライブラリ、エラー表現）。広がる前なら少し考える。広がった後に戻すなら、途中で止められる小さな改善を積み重ねる

比較が不利でも「前に行う」を選ぶときは理由を書く。書けないなら「直後」か「後回し」。迷ったら timing-and-discipline.md の 1〜2 節を読む。

### 「構造改善なし」の反証（D1〜D3）

「構造改善なし」とは、目的の振る舞い変更の「前」または「直後」に予定した構造改善が 0 件の計画を指す。結論にする前に、次の発火条件を観測できる事実（2d の記録）で判定する。

- D1: 目的の変更が、本番コード（テストを除く）の 2 か所以上から呼ばれる判定・計算の「既存の条件または式」を書き換える。または、2 か所以上に書かれている判定式を書き換える。データ項目の並び（設定フィールドの列など）は判定・計算ではない。
- D2: 目的の変更のために引数を足すと、関数の引数の数が lint / 型検査の閾値を超える。閾値はプロジェクトの設定ファイルの値、未設定ならツールの既定値（例: clippy `too_many_arguments` = 7、pylint `max-args` = 5）。引数はそのツールの数え方で数える。
- D3: 目的の変更が、ロジックが重複した同じ複数文のブロック（5 行以上）の 3 つ目以降のコピーを作る。単一の式や述語が複数箇所にあるのは D3 ではない（D1 だけで判定する）。除外: 定数・列挙値だけが違う 25 行以下の薄い委譲 / ラベル・キー・バインディング・定数だけが違う宣言ブロック（UI 項目、設定項目、登録項目） / 表への登録分岐・登録項目の追加 / 言語別の表への項目追加 / 既存の拡張点の新しい実装（既存インターフェースが求める形に従う新しい provider・handler・module）。

打ち消しは次の型の事実だけが有効で、それ以外は打ち消しにならない。

- D1: 「対象ロジックへの変更は追加のみ（既存の条件・項目・式を変えず、分岐・列挙項目・後段の処理を足すだけ）」。トークン単位で判定し、書式の違いは無視する。呼び出し元が変わらないことだけでは追加のみにならない。/ 「統一すると既存の永続化キー・保存データ・公開値が変わる（file:line）」。
- D2: 「閾値を超えない（設定ファイルとツールの既定値を確認済み）」/ 「引数をまとめる既存の型に引数を足す」。警告の抑止（`#[allow(...)]` など）は打ち消しではない。
- D3: 「各コピーは意図的に異なる振る舞いを持つ（違いの行番号）」/ 「統一すると既存の永続化キー・保存データ・公開値が変わる（file:line）」。
- 打ち消しにならないもの: 呼び出し元が少ない、変更頻度が低い、「機能の中で一緒に変えれば足りる」。

帰結: Dn が発火し、有効な打ち消しがなければ、対応する構造改善を「前」または「直後」に必ず入れる（後回し不可）。その計画では「構造改善なし」は有効な結論にならない。対応する構造改善は、D1: 判定・計算を名前付きの関数に抽出し、呼び出し元ごとに特性テストで現在の振る舞いを固定する（呼び出し元ごとに意味が違うなら関数を分ける）。D2: 引数をまとめる型を導入する（既存の型があればそれに寄せる）。D3: 共通部分を抽出する。Dn の対応改善は、「直後」の 3 条件を満たさなければ「前」に入れる。この扱いは、後回しの判別、手順 5 の「楽になる部分を書けない項目は後回し」、停止条件より優先する。打ち消しが成立した Dn と、発火しなかった候補は「後回し」「行わない」を選べる。

「前」も「直後」も 0 件で、かつ発火して打ち消しのない Dn が無いなら、結論は構造改善なし。テンプレートの固定文言（「該当なし（構造改善なし）」）で書き、`なし判定:` 欄、理由、振る舞い変更のコミット分割を示す。

## 手順 5: 手法を選び、順序つきの計画にする

techniques.md 冒頭の 2 つの表で手法を選び、選んだ手法の項だけを読む。

- 準備として入れるのは小さな構造改善（1 コミット・振る舞い不変）だけ。新しい抽象、モジュール分割、サービス分割は「範囲外の別計画」へ回し、入れるなら戻せる段階に分ける。
- 各項目に `[構造]` / `[振る舞い]` / `[テスト]` のラベルを付ける。`[構造]` には次の 3 つを一文ずつ書く。
  - 楽になる部分: 目的の変更（「直後」なら次の変更）のどこが楽になるか。可能なら「N か所 → M か所」。PR 説明にも書く。
  - 変わりうる振る舞い: 関数・入力・出力・順序・エラー経路のどれかで具体的に書く。一般例の表を写すだけでは不可。思い当たらないなら、確認した入力・呼び出し元（N か所）・出力・エラー経路の有無を添える。
  - 固定する方法: その振る舞いを固定するテストまたは確認方法。
- 楽になる部分を書けない項目は計画に入れず、実行もせず、後回しリストへ（目的の変更で触らない箇所の削除・改名・書き方の統一が典型）。計画モードでは、ここで計画テンプレートを出力して終える。

## 手順 6: 実行する（実行モード）

timing-and-discipline.md の「実行の規律」節に従う。要点:

1. 着手前に、触る範囲の振る舞いを固定するテストを確認する。なければ特性テスト（今の挙動をそのまま記録するテスト）を先に独立したコミットで書く。計画の「固定する方法」もここで用意する。
2. 1 コミット 1 改善。抽出・移動・改名・定数化・書き方の統一（`var` → `let` など）は、同じ関数への変更でも種類ごとに別コミットにする。目的の変更を楽にしない改名・書き方の統一は行わず後回しリストへ。各コミット後にテストを通す。コミットメッセージに種別（`refactor:` / `feat:` / `fix:` / `test:`）を付ける。
3. 構造改善と振る舞い変更は別コミット、原則として別 PR。PR は小さく保つ（構造改善を詰め込むほど衝突・意図しない振る舞い変化・無関係な改善が増える）。PR 説明には次の変更が何か所・どの程度で済むかを書く。確認を軽くする運用は、チームの合意を前提とした提案に留める（「まとめる量」）。
4. 時間の上限: 「前に行う」構造改善は合計 1 時間程度を目安にする。超えたら手を止め、最小限に絞れているか見直す。それでも超える場合は理由を計画に書く。
5. コミット前に、計画の「変わりうる振る舞い」と、見落としやすいもの（戻り値の型、評価・初期化順序、同じ値で意味の違うリテラルの統合、例外 / エラー経路、公開 API・シリアライズ形式）が変わっていないか確かめる。
6. 混ざったら「そのまま出して明示する / `git add -p` で分け直す / 破棄してやり直す」から選ぶ。説明できるなら分け直し、できないならやり直す。やり直すときは利用者の同意を得て `git stash push -u` か退避ブランチに保存し、`git reset --hard` などで捨てない。エージェントが書いていない変更には触れない。push 済みコミットは書き換えず、force push は利用者の明示的な指示があるときだけ行う。
7. 停止条件: 目的の変更が簡単に書ける状態（1〜2 か所に収まり、何を書くか迷わない）になったら構造改善をやめ、残りは後回しリストへ。実行中に見つけた改善も、楽になる部分を一文で書けなければ実施しない。

## 計画テンプレート（計画・実行モードで出力）

構造改善なし（「前」「直後」の構造改善が 0 件。発火して打ち消しのない Dn があれば選べない）の場合、`[構造]` 欄・停止条件・時間の上限には「該当なし（構造改善なし）」とそのまま書き、「振る舞い変更のコミット分割」行を必ず書く。

```markdown
## 結論
<構造改善あり / 構造改善なし>。<なしの場合: 理由（比較の向き、回収の見込みなど）>
なし判定: D1 <非発火 / 発火→打ち消し 事実 #n / 発火→構造改善あり>、D2 <同>、D3 <同>
## 対象の変更
<手順 1 の一文>
## 構造メモ
### 事実確認表
| # | 主張 | 種別（存在 / 否定 / 肯定 / 経路 / 履歴） | 確認したもの（検索コマンドまたは file:line） | 結果 | 判定（確認済 / 未確認） |
```

## バックログモード

1. `change_coupling.py` を期間を変えて実行し（直近 3 か月と 12 か月）、変更回数の上位と同時変更ペアを得る。
2. 上位ファイルを手順 3 で分類し、「変更回数が多い × 変えにくい」の順に並べる。変えにくくないファイルや変更回数が少ないファイルは、読みにくくても優先しない。
3. 各候補の次の変更を予想して一文にする（手順 1 に接続）。予想できない候補は優先度を下げる。
4. 出力: 優先順位つきの候補表（ファイル、変更回数、主な同時変更相手、原因、想定する次の変更、推奨手法、規模）。範囲外の別計画は分けて書く。
